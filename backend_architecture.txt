================================================================================
Daber Backend - System Architecture & Data Connection Walkthrough
================================================================================

This document details the Express + TypeScript backend architecture for the Daber 
application, explaining its directory structure, data models (Firestore), and 
how information flows between the client, backend, database, and AI systems.

--------------------------------------------------------------------------------

2. DATA CONNECTIONS & FIRESTORE DATABASE SCHEMA
--------------------------------------------------------------------------------

Daber utilizes a hierarchical Firestore database layout, organizing scenarios and 
sessions as subcollections of individual users. This guarantees clean data 
isolation and ownership.

Hierarchy:
  /users/{uid}                      <-- Root Collection
       │
       └── /scenarioSessions/{sessionId}  <-- Subcollection

----------------------------------------
A. The `users` Model (/users/{uid})
----------------------------------------
Stores account metadata, onboarding preferences, and progress tracking:

{
  "uid": "string",                 // Matches the authenticated Firebase UID
  "email": "string | null",        // Registered email address
  "displayName": "string | null",  // Student's full name
  "photoURL": "string | null",     // URL to profile avatar
  "createdAt": "Timestamp",        // Profile registration time
  "updatedAt": "Timestamp",        // Profile modification time
  "onboardingCompleted": "boolean",// Toggled true once onboarding is finished
  "onboarding": {
    "native": "string",            // Native language (e.g., "English", "Spanish")
    "level": "string",             // CEFR Proficiency Level (e.g., "A1", "A2", "B1")
    "goal": "string",              // Target motivation (e.g., "travel", "work")
    "voice": "string"              // Preferred AI Voice Character (e.g., "dana", "noam")
  },
  "completedStops": ["string"]     // Array of completed roadmap milestone IDs
}

----------------------------------------
B. The `scenarioSessions` Model (/users/{uid}/scenarioSessions/{sessionId})
----------------------------------------
Stores details of the conversations, transcripts, and voice assessment scores:

{
  "sessionId": "string",            // Unique UUID identifier
  "provider": "gemini | openai",    // Selected LLM backend powering the conversation
  "theme": {
    "id": "string",                 // Theme ID (e.g., "supermarket", "cafe")
    "title": "string",              // Human-readable title
    "he": "string",                 // Hebrew translation of theme
    "band": "string"                // CEFR level band target (e.g., "A2–B1")
  },
  "variation": {
    "id": "string",                 // Variation identifier (e.g., "friday-rush")
    "label": "string",              // Human-readable scenario name
    "situation": "string"           // Specific contextual prompt guidance
  },
  "tutorVoice": {
    "id": "string",                 // Voice character ID ("dana", "noam", "shira")
    "name": "string",               // Tutor display name
    "subtitle": "string"            // Character voice traits description
  },
  "learnerProfile": {
    "native": "string | null",
    "level": "string | null",
    "goal": "string | null"
  },
  "conversation": {
    "title": "string",              // e.g., "Dana · Supermarket"
    "starterLine": "string",        // Starting prompt text issued by tutor
    "promptSeed": "string"          // System prompt built for this scenario/learner
  },
  "turns": [                        // Ordered log of turns
    {
      "role": "learner | tutor",
      "text": "string",             // Message text in Hebrew
      "createdAt": "string",        // Timestamp ISO string
      "inputMode": "voice | text",  // Optional mode indicator
      "pronunciation": {            // Pronunciation scores (Voice mode only)
        "overallScore": 85,         // Average grade (1-100)
        "accuracyScore": 82,        // Syllabic matching grade (1-100)
        "fluencyScore": 88,         // Speech rate and pause analysis grade (1-100)
        "feedback": "string",       // Short actionable coaching statement
        "scoringMode": "audio | transcript",
        "issues": [                 // Phonetic errors detected
          {
            "label": "string",      // e.g., "TZADI", "SOUND"
            "issueCount": 1,
            "severity": "low | medium | high",
            "affectedWord": "string", // Word containing error (e.g., "ביצים")
            "expectedSound": "string", // Correct sound (e.g., "ts")
            "heardApproximation": "string", // Heard approximation (e.g., "s")
            "hint": "string"        // Practice instruction
          }
        ]
      }
    }
  ],
  "supportTranslations": {          // Translations cache to save API usage
    "English": {
      "sha1HashKey": {
        "sourceText": "Hebrew text",
        "translation": "English translation"
      }
    }
  },
  "createdAt": "Timestamp",
  "updatedAt": "Timestamp"
}

3. COMPONENT INTERACTIONS & SYSTEM DATA FLOW
--------------------------------------------------------------------------------

The system operates via five main integration pathways:

1. User Authentication & Profile Synchronization
   - The user authenticates on the Client app using the Firebase Auth SDK.
   - The Client POSTs the Firebase token to `/auth/sync-user`.
   - The Backend verifies the token using the Firebase Admin SDK.
   - It writes/syncs the profile parameters into Firestore under `/users/{uid}`.
   - The Backend returns custom access & refresh JWT tokens (signed with a local 
     cryptographic secret via HMAC-SHA256). Subsequent requests use these JWTs
     instead of verifying with Firebase every time, drastically reducing latency.

2. Onboarding Setup
   - The client app sends the user's questionnaire answers to `/onboarding`.
   - The backend validates the inputs (valid CEFR levels, goals, native languages, 
     and voices) and merges them into `/users/{uid}`.

3. Scenario Launch
   - The client requests a scenario session by hitting `/scenarios/launch` with a 
     selected theme (e.g., "cafe").
   - The backend pulls the learner profile (`level`, `goal`, `native`, `voice`) 
     from `/users/{uid}`.
   - It picks a random scenario conversation type and variation (e.g., "sold out 
     croissants") from `scenarioCatalog.ts`.
   - It stores the session metadata inside the subcollection document 
     `/users/{uid}/scenarioSessions/{sessionId}` and responds to the client.

4. Message & Turn Processing (Text or Voice)
   - For Text turns: The learner's Hebrew message is appended to the session `turns` 
     array. The backend feeds the prompt history to Gemini or OpenAI, and 
     records the response.
   - For Voice turns: The client uploads base64 WebM/M4A audio.
     - Gemini Mode: Sent directly to Gemini 2.5/Flash Multimodal API. It transcribes,
       evaluates pronunciation, and answers in one request.
       OpenAI Mode: Sent to Whisper for transcription first. The transcript is 
       then fed to GPT to grade pronunciation (comparing reference vs transcript)
       and generate the tutor's response.
     - All results (transcript, score metrics, tutor response) are updated in 
       the session document.
     - Websockets (Socket.IO) are available as an alternative via 
       `realtimeScenarioServer.ts` to stream these turns in real-time.

5. Translation Cache
   - In order to optimize billing and speed, translations of tutor lines are 
     cached locally. When the client POSTs to `/scenarios/sessions/{sessionId}/translate`,
     the backend generates a SHA-1 hash of the Hebrew sentence and checks the
     session's `supportTranslations` mapping. Only if it is not cached does it 
     call the AI translation model.

5. DEDICATED CONVERSATION TURN LIFECYCLE (HTTP VS SOCKET.IO)
--------------------------------------------------------------------------------

When the learner interacts inside a scenario conversation, the system processes 
turns through either stateless HTTP POST requests or a stateful WebSocket connection.

============================================
CONVERSATION VIA HTTP REST API (Stateless)
============================================

   Client (App)                 Backend Server                 Firestore / LLM
        │                              │                              │
        ├────── (1) POST Turn ────────►│                              │
        │   (Text Message or Audio)    ├────── (2) Load Session ─────►│
        │                              │   Get prompt seed & history  │
        │                              │◄─────── [Session Data] ──────┤
        │                              │                              │
        │                              ├────── (3) Run LLM Engine ───►│
        │                              │   Send Prompt to OpenAI/Gem Gemini
        │                              │◄──────── [LLM Response] ─────┤
        │                              │                              │
        │                              ├────── (4) Update DB ────────►│
        │                              │   Append turns to Document   │
        │                              │                              │
        │◄───── (5) JSON Response ─────┤                              │
        │   (Tutor reply + scores)     │                              │

============================================
CONVERSATION VIA SOCKET.IO (Real-Time Duplex)
============================================
To enable micro-interactions like displaying the transcript instantly or showing 
"Dana is typing..." (tutor pending status), Socket.IO splits voice turn 
processing into multi-stage events.

   Client (App)                 Backend Server (Socket.IO)     Firestore / LLM
        │                              │                              │
        ├───── (1) join_room ─────────►│                              │
        │   [sessionId]                ├───── (2) Join room ─────────►│
        │                              │   Verify token & ownership   │
        │                              │                              │
        ├──── (3) Emit Turn ──────────►│                              │
        │ (scenario:voice_turn w/ Audio)│                              │
        │                              ├───── (4) Transcribe Audio ──►│
        │                              │   Call Whisper/Gemini STT    │
        │                              │◄─────── [Transcript] ────────┤
        │                              │                              │
        │◄── (5) Emit learner_turn ────┤                              │
        │    (Instant transcript)      │                              │
        │                              │                              │
        │◄── (6) Emit tutor_pending ───┤                              │
        │    (Show typing indicator)   │                              │
        │                              │                              │
        │                              ├───── (7) Async Run AI ──────►│
        │                              │   Compute pronunciation &    │
        │                              │   generate conversational reply
        │                              │◄───── [Scores & Tutor Text] ─┤
        │                              │                              │
        │                              ├───── (8) Update DB ─────────►│
        │                              │   Save turns to document     │
        │                              │                              │
        │◄── (9) Emit turn_update ─────┤                              │
        │    (Send learner scores)     │                              │
        │                              │                              │
        │◄── (10) Emit tutor_turn ─────┤                              │
        │    (Send next tutor text)    │                              │
